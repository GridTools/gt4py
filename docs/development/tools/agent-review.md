# Agent Review

The `Agent Review` workflow ([`.github/workflows/agent-review.yml`](../../../.github/workflows/agent-review.yml)) posts an advisory review of a pull request written by a coding agent (a _harness_ such as opencode or Pi) that can explore the repository with tools. The agent runs inside the [AWF](https://github.com/github/gh-aw-firewall) sandbox, without network access, and uses the [CSCS inference service](https://docs.cscs.ch/services/inference/) through AWF's API proxy. It is designed so that neither the inference key nor a write-capable token is readable by the agent or by code from the PR. It is **never a required status check**: if the agent fails or times out, the run stays green with a warning annotation. It runs independently of [PR Agent](pr-agent.md), and uses no comment commands, so it does not interfere with PR Agent's.

The design and the alternatives considered are in [ADR 0001](../ADRs/ci/0001-sandboxed-agent-pr-review.md).

> [!WARNING]
> Pilot, run on a fork only, from `push`-triggered test branches; not yet run in GridTools/gt4py (see [Required repository settings](#required-repository-settings)). Never exercised there: the `pull_request_target` and `workflow_dispatch` triggers, the `agent-review` label, a non-writer being denied, a PR from another repository, and the key-isolation canaries with the final AWF flags (they ran in separate configurations in the AWF probe). In the hostile-PR suite the real harnesses did not attempt the injected attacks, so those runs show that the models complied with the prompt, not that the sandbox contained them; containment rests on the canary and offline tests. No invariant deviation was observed, and no key material appeared in the artifacts or comments.

## Required repository settings

Without these, the workflow does not run, or runs without a key.

1. **An Actions event policy that allows `pull_request_target`** for this workflow. GitHub blocks `pull_request_target` by default in public repositories from **2 December 2026** (brownouts before that), unless an applicable policy explicitly allows it: the label path then stops working (during the brownouts, GitHub creates a failed run with an error annotation instead of running the workflow). Under **Settings → Actions → Policies** (a repository administrator or organization owner; API: `/repos/{owner}/{repo}/actions/policies`), add a policy scoped by workflow path to `.github/workflows/agent-review.yml` that allows the events this workflow uses, **`pull_request_target` and `workflow_dispatch`**: event rules read as an allowlist, so listing `pull_request_target` alone would probably block dispatches. The docs do not say how several policies combine; check the result in evaluate mode (Insights) where available before enforcing it. PR Agent's policy (see [pr-agent.md](pr-agent.md#event-policy)) is scoped to `.github/workflows/pr-agent.yml` only and does not cover this workflow. See [Control workflow execution](https://docs.github.com/actions/how-tos/administer/control-workflow-execution). `workflow_dispatch` is not blocked by default.
2. **The `agent-review` environment, restricted to the default branch** (**Settings → Environments → agent-review → Deployment branches and tags → Selected branches**: the default branch only), holding the secret **`AGENT_REVIEW_INFERENCE_API_KEY`**. Only the `review` job uses the environment. The restriction keeps the key from branch workflows and from dispatches of another ref; `pull_request_target` runs with the default branch as its ref, so it should pass (not yet observed). Each run of the `review` job records a deployment to this environment. GitHub creates the environment, unprotected and empty, the first time the workflow runs without it; the review is then skipped with a notice.
3. **A dedicated CSCS key** in that secret, never PR Agent's `CSCS_INFERENCE_API_KEY`: created in the [inference UI](https://ui.inference.cscs.ch/login) for this workflow alone, with its own token budget and reset period, and restricted to the configured model. **Its budget is the only hard spending cap** (see [What remains risky](#what-remains-risky)). The key also works for `/v1/completions`, `/v1/responses` and `/v1/messages` (checked on the fork's key), and signs in to the inference UI.
4. The repository variables in [Configuration](#configuration).

**Deployment state in GridTools/gt4py (2026-11-13)**:

- The `agent-review` environment exists, restricted to `main`, and holds the dedicated key in `AGENT_REVIEW_INFERENCE_API_KEY` (item 3).
- The repository variables are `AGENT_REVIEW_HARNESS=opencode` and `AGENT_REVIEW_MODEL=zai-org/GLM-5.3-Flash`.
- **No event policy covers this workflow yet**: the only one, "Allow PR Agent events" (policy 13604), allows `pull_request_target` and `issue_comment` for `.github/workflows/pr-agent.yml` alone. A policy for `.github/workflows/agent-review.yml` allowing `pull_request_target` and `workflow_dispatch` (item 1) must be added before the label path can run after 2 December 2026. Until then, the workflow can still be started with **Run workflow** once merged, since `workflow_dispatch` is not blocked by default, and such a run uses the key.

## Usage

- Anyone with write access can request a review of any PR not opened by a bot, including a fork or draft PR, by adding the **`agent-review` label**. The **labeller's** permission is checked, not the author's. To review again, remove and re-add the label. Pushes to the PR do not trigger a review.
- **Run workflow** on the Actions tab (`workflow_dispatch`) reviews a given PR number, optionally with another harness or as a dry run that only shows the comment in the run summary.
- **Not enabled yet**: an automatic review when a non-draft PR is opened, reopened or marked ready by an author with write access. The `Authorize` step handles it, but the trigger types are commented out until the label and dispatch paths have been observed upstream. When enabled, note that a `triage` user can close and reopen a writer's PR to start one run per cycle.
- Write access comes from the same teams and accounts as for PR Agent (see [pr-agent.md](pr-agent.md#usage)). `triage` is not enough: the permission API reports it as `read`.

Each harness keeps one comment per PR, updated in place by later runs. The comment names the harness, its version, the model and the reviewed commit; pushes after that commit are not reviewed.

## How it works

| Job         | Holds                                                            | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `authorize` | read token                                                       | Checks permissions (fails closed on API errors), pins the PR head and base sha, resolves the harness and model. Every other job requires its `allowed` output.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `prepare`   | read token, **no secrets**                                       | Runs the harness's `install.sh` from the workflow's own commit, which downloads the pinned harness without running any of its code (no install scripts; the version is checked later, inside the sandbox), and uploads it as an artifact.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `review`    | read token; inference key in **one step's** env (`agent-review`) | Copies [`.github/agent-review/`](../../../.github/agent-review/) from the workflow's own commit to `/opt/agent-review` (root-owned, read-only in the sandbox), writes the PR metadata as raw bytes, and runs AWF twice. First without a key and with only `github.com` allowed: [`run-review`](../../../.github/agent-review/bin/run-review) `--phase fetch` fetches the PR with git, resets agent instruction files to the base version and renders the prompt; no agent runs. Then with the key and no allowed domain: `run-review --phase review` runs the harness. Afterwards leftover containers are removed and [`collect-result`](../../../.github/agent-review/bin/collect-result) copies only `review.md` and `meta.json` out. |
| `publish`   | write token (`pull-requests`), no model                          | On a fresh VM, [`publish-comment`](../../../.github/agent-review/bin/publish-comment) validates and renders the review in a step without a token, then upserts the comment.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

The review rules are in [`prompt.md.tmpl`](../../../.github/agent-review/prompt.md.tmpl), which points the agent at `.github/copilot-instructions.md`, `AGENTS.md`, `CODING_GUIDELINES.md` and `src/gt4py/next/AGENTS.md`. Extend those files rather than the prompt. The PR title and body are included as delimited untrusted data. The prompt also asks the agent to finish within about 12 minutes (the harness limit is 20), to read narrowly, to confirm each finding against the code and say how, and to keep maintainability remarks to an optional `### Nits` section of at most three lines; the comment has `### Summary`, `### Findings` (at most five), and optionally `### Nits` and `### Questions`.

## Security invariants

The workflow uses `pull_request_target` because most GT4Py PRs come from forks, which get no repository secrets under `pull_request`. That trigger runs with secrets next to untrusted code, so all PR content is handled inside AWF only. Keep these when changing it:

01. **The real key is only in AWF's API-proxy sidecar** and the environment of the `awf` step that runs the agent; the agent sees placeholders. Never inline it into a `run:` script or pass it to another step. It comes from the `agent-review` environment, never from a repository secret.
02. **No PR-derived byte is executed or parsed on the host.** No `actions/checkout`, no `uv sync`, no git on the PR tree outside the sandbox. `pr.json` is written as bytes and parsed inside the sandbox. The one exception is AWF's token-usage log, which the API-proxy sidecar writes out of the sandbox's reach; its request paths and model names come from the agent's requests, so the `Report token usage` step reads only its numeric fields. `prepare` never executes harness code either: it runs on the host with sudo, and its token can read and write the Actions cache.
03. **The sandbox writes only to the review workspace** (`filesystem.allowWrite`); the rest of what AWF mounts from the host (the runner workspace, `/tmp`, `~/.config`, `~/.local/bin`, ...) is read-only to it. Exception: `~/.copilot/{logs,session-state}` stay writable, and AWF moves them into host `/tmp` after the run. So **the host is treated as tainted once `awf` returns**: steps after the agent's run use no token, run no git, use no cache action, and run only `/usr/bin` tools with a fixed `PATH`. The only data leaving `review` is at most 64 KiB per file of regular, single-link files named `review.md` and `meta.json`, copied without following symlinks, after every sandbox container has been removed, plus the token counts in the run summary and, if `AGENT_REVIEW_UPLOAD_AUDIT` is set, AWF's own audit and proxy logs from `$RUNNER_TEMP`.
04. **The agent has no network access** except AWF's API-proxy listener: its sandbox run allows no domain. Only the first, keyless run, which runs no agent, reaches `github.com`. AWF still allows the inference host for its sidecar in the shared egress proxy, so the agent can probably reach it directly too (not tried), without a key.
05. **Write tokens exist only in `publish`**, which runs no model and no PR code, and treats the review as hostile: it must be valid UTF-8; invisible format characters (zero-width, bidirectional controls, variation selectors, tag characters) are dropped; markup that GitHub renders as nothing (HTML comments, processing instructions, declarations, CDATA, link reference definitions) is broken up, so the review cannot hide text that way nor imitate the comment marker; character references are escaped (`&#64;` and `&commat;` would become mentions, `&rlm;` an invisible character); `@mentions` are neutralised with a zero-width joiner; the length is capped. Rendering needs no token. The marker is matched only on the first line of the bot's own comments, never with `--edit-last`, because PR Agent posts as the same bot.
06. **Harness, prompt and AWF configuration come from the workflow's own commit** (`github.workflow_sha`, fetched as a tarball), never from the PR, so a PR cannot change the policy it is reviewed by. **Instruction files** matching [`instruction-files.txt`](../../../.github/agent-review/instruction-files.txt), at any depth, are reset to the version in the PR's **base commit** (or removed): that is the branch the PR targets, which may be any upstream branch, not necessarily the default one. The PR's versions are kept as data for the review. Every file [`prompt.md.tmpl`](../../../.github/agent-review/prompt.md.tmpl) tells the agent to _follow_ (`AGENTS.md`, `CODING_GUIDELINES.md`, `.github/copilot-instructions.md`, nested `AGENTS.md`) must be in that list, or a PR could inject instructions into it; `tests/test-instruction-coverage.sh` checks this.
07. **The `review` job starts no service on the host.** The sandbox can connect to any host port bound to `0.0.0.0` through AWF's network gateway (`172.30.0.1`); on a stock runner that is only `sshd`. No `services:` containers, no daemons started in a step.
08. **AWF's logs are read only from `$RUNNER_TEMP`** (`--proxy-logs-dir`, `--audit-dir`). Without `--proxy-logs-dir`, AWF moves them to `/tmp` after the run, where the sandbox can plant fake ones.
09. **Only AWF's OpenAI listener is configured**: never an `anthropic` target or `ANTHROPIC_API_KEY`. In AWF v0.29.12 the Anthropic listener's `POST /messages` is not counted by `maxTurns`, and the key breaks the entrypoint under `filesystem.allowWrite`. The run log shows `API proxy enabled: OpenAI=true, Anthropic=false`.
10. **Pinned**: actions by commit SHA, the runner image (`ubuntu-24.04`, which is the sandbox's userland since AWF chroots into the host filesystem), the AWF version, AWF images by digest (the setup action's `image-tag` output, taken from the attested release at run time), and each harness by exact version with an integrity check. Not pinned: the runner image's own updates, and the CSCS model behind its id.
11. **The sandbox's output cannot issue workflow commands**: every line of `awf` output is prefixed. Harness diagnostics go through `diag` in `common.sh`, which does the same.

## What remains risky

- **Prompt injection can steer the review's content**: a false approval, misleading findings, links. Mitigations: the comment is labelled advisory, never a status, names the reviewed commit and says the PR can steer it; mentions are neutralised and the size is capped. Cross-references such as `owner/repo#123` are not neutralised and can create backlinks in other repositories. The prompt-named rule files are reset to base (invariant 6), but files they in turn point at (`CONTRIBUTING.md`, the ADRs) are not, so injected text there is still read as context; it can only steer review content. Visible content (links, images, collapsed `<details>`) is not filtered.
- **Budget burn, driven by the content of any reviewed PR.** The agent has a shell and can call AWF's listener directly, so the per-run bound is AWF's rate limiter, not the turn cap: at most **100 upstream requests per run** (`rateLimiting.requestsPerHour`; the run is shorter than an hour), paced at 30 per minute, each up to the model's context and output limits. AWF's `maxTurns` (80) stops a well-behaved harness but is not a hard cap: it counts only `POST`s to chat-completions, responses and messages paths, when the response ends. Other paths are forwarded with the real key and not counted (the key works for `/v1/completions`), and concurrent calls are all admitted before any is counted. AWF forwards every method and path under `/v1` (dot segments cannot leave `/v1`; encoded separators such as `%2f` are passed through), has no `max_tokens` clamp, and skips the model allowlist when the body has no string `model` or is not JSON. All of this was checked on the fork against a fake upstream: 100 concurrent chat calls all reached it under a turn cap of 20, and 100 calls to uncounted paths reached it under the production limits before the hourly limit answered 429. Hence the dedicated key's budget (Required settings, item 3) is the real cap.
- **A sandbox escape** would expose the key on the host. Beyond kernel and Docker bugs, this includes AWF itself: it runs as root on the host, and its API-proxy sidecar, which holds the key, parses requests from the sandbox; both are young code (the AWF probe worked around three of its bugs). Mitigations: the dedicated, low-budget key, quick to rotate; gVisor (`--container-runtime gvisor`) is planned once the harnesses are known to work with it.
- **Egress**: the keyless fetch run reaches `github.com` and its subdomains, with git only. The agent's run reaches the API proxy, the inference host (without a key) and the runner's `sshd` through AWF's gateway, and runs for up to 25 minutes.
- **Live logs**: the review step's log shows the agent's output (prefixed) while it runs; it carries no secret.
- `@`, `&` and `]:` are neutralised everywhere, including code blocks, so a Python decorator copied from a review contains an invisible character, and character references show literally.

## Configuration

The key and the event policy are under [Required repository settings](#required-repository-settings).

| Variable                    | Default                            | Purpose                                                                                                                   |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `AGENT_REVIEW_HARNESS`      | **required**                       | `opencode` (recommended), `pi` or `stub`; the `workflow_dispatch` input overrides it                                      |
| `AGENT_REVIEW_MODEL`        | **required** (except for `stub`)   | CSCS model id, as listed by `GET /v1/models` (recommended: `zai-org/GLM-5.3-Flash`); also the only model AWF lets through |
| `AGENT_REVIEW_API_BASE`     | `https://api.inference.cscs.ch/v1` | OpenAI-compatible endpoint                                                                                                |
| `AGENT_REVIEW_UPLOAD_AUDIT` | unset                              | `true` uploads AWF's audit and proxy logs (requests, tokens, egress) as an artifact                                       |

**Recommended**: `opencode` with `zai-org/GLM-5.3-Flash`; `pi` with the same model is the alternative (more findings per PR, 1.5–2× the tokens). `zai-org/GLM-5.3` (non-Flash) with opencode is not recommended at the current caps: on real PRs it produced no review, timing out at the 20-minute harness limit. This is from a quality evaluation of dry runs on three merged upstream PRs.

Fixed limits, changed by a reviewed PR ([`awf.yaml`](../../../.github/agent-review/awf.yaml)): 100 requests per hour and 30 per minute to the API proxy (the per-run bound), `apiProxy.maxTurns` 80 (stops a well-behaved harness; opencode also stops itself after 35 steps, Pi has no cap of its own), 20 minutes for the harness, 25 for AWF's `agentTimeout`, 30 for the review step and 45 for the job. AWF's AI-credit cap is not used, since it prices CSCS models with an estimate, after the response.

AWF's runtime model catalogue is disabled (`apiProxy.modelCatalogue.enabled: false`): otherwise its API-proxy sidecar makes ~7 GETs per run to `api.github.com` (`github/gh-aw-firewall`'s pricing snapshot). Those carry no data about the run and no token, but the AI-credit accounting they feed is unused here. Note that the inference host (added via `baseUrlEnv`) is marked _sensitive_ by AWF and is therefore excluded from Squid's `access.log` and `audit.jsonl`, so model traffic does not appear in the egress logs by design; it is visible only in the API-proxy's own `token-usage.jsonl`.

The `stub` harness makes no model call and posts a fixed review containing hostile content; it is for testing the pipeline only.

## Harness adapters

A harness is a directory `.github/agent-review/harnesses/<name>/`; the name must also be added to the `workflow_dispatch` choice and to the `case` in the `Authorize` step. The contract is in [`harnesses/README.md`](../../../.github/agent-review/harnesses/README.md); in short:

- `install.sh <prefix>` runs in `prepare` and installs an exact version, integrity-checked, into `<prefix>`, writing the version to `<prefix>/VERSION`, without executing any harness code. The prefix is unpacked to `/opt/agent-review/harness/<name>` and must run from there without network access.
- `run.sh` runs inside the sandbox, from the PR checkout, with `PROMPT_FILE`, `REPO_DIR`, `OUT_DIR`, `CONTEXT_DIR`, `MODEL`, `HARNESS_PREFIX` and `PR_NUMBER` set, plus AWF's `AWF_API_PROXY_OPENAI_URL`. It checks the harness version, keeps its configuration in a scratch home under `$TMPDIR` (in the workspace), disables updates, telemetry and sharing, and writes `$OUT_DIR/review.md`. Exit codes: 0 review written, 2 no review, anything else a failure; it must return 2, not 0, when the harness exits 0 without a real answer.
- `wire` says whether the harness calls a model: `openai-chat` (through AWF's OpenAI listener) or `none`.
- File names the harness reads as instructions or configuration, at any depth, go into `instruction-files.txt`.

The [adapters README](../../../.github/agent-review/harnesses/README.md) compares the harnesses (version, wire, how the repository's own agent configuration is disabled, turn cap); each adapter's `README.md` explains its pins, upgrades and isolation. In short: both use the OpenAI chat API on AWF's OpenAI listener, the only one configured (AWF v0.29.12 must not get `ANTHROPIC_API_KEY`: its Anthropic listener's `POST /messages` escapes the turn count, and its entrypoint fails under `filesystem.allowWrite`); opencode and Pi have switches that ignore the repository's agent configuration (which can otherwise execute code from the PR).

## Testing changes

`pull_request_target` and `workflow_dispatch` read the workflow from the default branch, so a change cannot be tested from a PR. To test on a fork:

1. Open a throwaway PR inside the fork to review and comment on.
2. On a branch named `ci/agent-review-<n>`, re-enable the two blocks marked `COMMENTED OUT` in the workflow (the `push` trigger and the `TEST_*` parameters, with the throwaway PR's number) and push it. Every push runs the pipeline with the `stub` harness unless `TEST_HARNESS` says otherwise; other harnesses need `TEST_MODEL` (or the `AGENT_REVIEW_MODEL` variable) and the `AGENT_REVIEW_INFERENCE_API_KEY` secret in the fork's `agent-review` environment. A push runs for its branch, so this only works while that environment is not restricted to the default branch (or does not exist yet). Never merge these blocks enabled.
3. To review a public PR of another repository (for example an upstream PR, to compare prompts or harnesses), also set `TEST_REPO` to its slug and, optionally, `TEST_HEAD_SHA` and `TEST_BASE_SHA` to review an older commit. Such a run is always a dry run, so it never comments on the fork's PR with the same number; the review is in the run summary and the `agent-review-result` artifact.

The scripts have offline tests: `bash .github/agent-review/tests/test-collect-result.sh`, `test-publish-comment.sh` and `test-instruction-coverage.sh`. `test-run-review.sh` runs the driver with the `stub` harness against a real PR, without AWF, in one run and in two phases (the second with git's network protocols disabled), and needs network access. To try an adapter without a key, run `install.sh <prefix>`, then `run-review` with `AWF_API_PROXY_OPENAI_URL` pointing at a local fake OpenAI server.
